## Identity and approval per surface

| Surface | Identity used | Approval point | Pattern |
|---|---|---|---|
| VS Code / CLI | Developer (`az login`, VS Code sign-in) | Per-tool prompts | P19, P20 |
| Copilot app | Developer, or a cloud sandbox | Mode-dependent; none in Autopilot | P22 (preview) |
| Cloud agent | Repository-configured MCP secrets in an Actions sandbox | The pull request | P21 |
| SDK | App identity or on-behalf-of user | Approvals you build in | P24 |

## Boundaries

- Surfaces **edit files and call tools**; Fabric Git integration or an approved scoped writer
  changes the workspace.
- The cloud agent's firewall limits its shell egress, not the MCP servers it starts — so its MCP
  list must be read-only or offline.
- Skills describe procedures; the surface executes them with whatever identity it holds.

## Trade-offs

- Local surfaces are interactive and approval-rich, but tied to one developer's session.
- The cloud agent scales a backlog but moves all review to the pull request.
- The Copilot app adds parallelism at the cost of preview status and autonomy risk.

## Online and offline

Every surface needs network access to its model. The `ffia-local` tools, synthetic data and
checks behind each step run offline; live read-only Fabric MCP profiles arrive in Phase 5.
