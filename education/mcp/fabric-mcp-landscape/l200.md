## Server comparison for architects

| Server | Host / transport | Identity | Read/write surface | Status |
|---|---|---|---|---|
| Fabric MCP Server (local) 1.4.0 | Local, stdio | None for docs; workstation credentials for live tools | `docs_*` read; `onelake_*` read + upload/delete; `core_*` create item; `datafactory_*` includes run pipeline | GA |
| Fabric IQ MCP | Remote, Streamable HTTP | Entra delegated | Read-only; discover models, metadata, DAX query; RLS/OLS enforced | GA |
| Power BI Authoring MCP | Local stdio (reaches PBIP and Desktop) or hosted HTTP (semantic models only) | Entra | Tables, relationships, measures, roles - write-capable | Local GA 1.0.0; hosted PREVIEW |
| Data Warehouse MCP | Remote; global or item-scoped endpoint | Entra; workspace + SQL permissions | One T-SQL execution tool - DDL and DML possible | PREVIEW |
| Ontology MCP | Remote, per ontology item | Entra (service principal limited) | Read | PREVIEW |
| Data agent MCP | Remote, one tool per published agent | Bearer token (user or service principal) | Read (questions) | Needs validation |
| Fabric Core MCP (remote) | Remote | Entra | Workspace, item and role management | Needs validation |
| RTI MCP | Local OSS and remote variants | Varies | KQL, Eventstream, Activator | Needs validation |

## Choosing a profile

The accelerator plans three Fabric profiles (Phase 5):

1. **Offline / docs** - local server docs tools only, plus Microsoft Learn. No tenant.
2. **Live read-only** - Fabric IQ MCP and read-only OneLake tools, pinned to a dev workspace.
3. **Live authoring** - Power BI Authoring MCP (local, against a sandbox PBIP copy) and other
   write-capable tools, opt-in and approval-gated. Data Warehouse MCP stays behind the
   `data_warehouse_mcp` preview flag.

## Boundaries and trade-offs

- **Remote read-only servers** are the easiest to govern: one identity path, server-side
  permission checks, no local credentials on disk.
- **Local servers** are powerful and convenient but inherit whatever the workstation is signed
  in as. Pin the tenant with `az login --tenant` and use a dev workspace.
- **Arbitrary T-SQL** turns a "query" server into a change server. Treat it like a database
  admin console.
- **Data leaving the boundary.** Answers flow into the MCP client and its model. Microsoft notes
  for the data agent endpoint that responses may leave Fabric's compliance boundary depending on
  the client used.

## Online vs offline

Only the local server's docs tools work without a tenant. Offline, the accelerator substitutes
`ffia-local`, whose tools (`inspect_medallion_architecture`, `preview_table`,
`evaluate_measures`, `detect_duplicate_records`) mirror the *shape* of Fabric questions over
synthetic data and are labeled `LOCAL` - never as a Fabric result.
