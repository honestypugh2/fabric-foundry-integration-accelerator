## Router internals

- **Timeout:** each live attempt runs inside `asyncio.timeout(timeout_seconds)`; a hang becomes
  `timed out after 5s` in the route decision.
- **Retries:** `tenacity` with `stop_after_attempt(max_retries + 1)` and
  `wait_exponential_jitter` (multiplier `backoff_seconds`, max `8 × backoff`, jitter
  `backoff_seconds`). The retry object is built *before* the live call, so a configuration error
  is never mistaken for an outage.
- **Classification:** `CLIENT_ERRORS` (unknown resource, invalid request) are excluded from
  retries and re-raised before any fallback or breaker change. Every other exception is the
  controlled translation boundary: it is redacted, described and counted as **one** breaker
  failure per request (not per attempt).
- **Fallback:** the LOCAL envelope is copied with `fallback_used`, `fallback_reason`,
  `requested_provider` and `operating_mode: HYBRID`. The execution label remains the label of
  what actually served the data.
- **No fallback:** a `RouteDecision` with outcome `UNAVAILABLE` is stored, an `UNAVAILABLE`
  audit record is written with `cloud_operation_performed: false`, and
  `CapabilityUnavailableError` becomes HTTP 503.

## Breaker state machine

```text
CLOSED --3 consecutive failures--> OPEN --60 s--> HALF_OPEN --success--> CLOSED
                                                   └--failure--> OPEN (timer restarts)
```

The clock is injectable, so tests drive transitions deterministically. State is in memory per
process: a restart resets it.

## Why writes never fall back

The router only exposes `read`. Writes go through the change service, which binds an approval to
a destination hash. An approved LIVE plan without an authorized writer raises
`LiveWriteUnavailableError`, and the simulated workspace is left untouched. Redirecting it would
turn an approval for one target into an execution on another, and would produce false evidence.

## Failure modes

| Failure | Risk | Control |
|---|---|---|
| Fallback hides a long outage | Audience believes data is live | Mode, `fallback_used` and reason in every envelope and audit record |
| Retry storm during throttling | Makes the outage worse | Bounded retries with jitter + breaker |
| Unknown table treated as outage | Masks a bug with synthetic data | Client errors bypass fallback |
| Breaker never re-closes | Stays degraded after recovery | HALF_OPEN trial after the reset timeout |
| Fault injector mistaken for a live call | False evidence | Kind `FAULT-INJECTION`; it never contacts any service |

## Production gaps

- Live Fabric REST and MCP throttling, status codes and `Retry-After` handling **require tenant
  validation** (Phase 5); budgets should be tuned per API.
- Breakers are per process; a scaled-out service needs shared state or accepts independent
  breakers deliberately.
- Retrying non-idempotent operations automatically is out of scope and should stay that way.
