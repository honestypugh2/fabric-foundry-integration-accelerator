## What runs in this repository today

P06 is the anchor, so most of the repository implements one of its hops. Start the control plane
with `make run-api` (or run everything at once with `ffia demo offline`).

```bash
# Context: a governed, bounded read through the provider router (LOCAL offline)
curl -s -X POST localhost:8000/api/v1/fabric/read -H 'Content-Type: application/json' \
  -d '{"operation": "list_tables", "lakehouse_id": "local-lh-hc-lab-7file-v1"}'

# Evaluation: compare the synthetic semantic model with the committed baseline
curl -s -X POST localhost:8000/api/v1/evaluations/run -H 'Content-Type: application/json' \
  -d '{"profile": "hc-lab-7file-v1", "observed_label": "LOCAL"}'

# Reasoning: offline, foundry_agent is served by the Local sales agent (LOCAL, not Foundry)
curl -s localhost:8000/api/v1/runtime/providers   # foundry_agent → LOCAL (Local sales agent)
ffia agents ask "What was total booked revenue last month?"  # label, provider, fallback, grounding, tool calls
ffia agents eval                                            # 5 cases, gate min_pass_rate 1.0

# Action and evidence: the P08 flow (see lab-governed-change)
curl -s -X POST localhost:8000/api/v1/plans ...   # then /approvals, /fabric/change
curl -s localhost:8000/api/v1/audit/<correlation_id>
```

Access goes through the `ffia-local` MCP server (`make run-mcp`, registered in `.mcp.json`):
`inspect_medallion_architecture`, `evaluate_measures` and `generate_fabric_change_plan` are the
read and propose tools an agent would use. There is no approve or execute tool.

## Mapping the offline demo to P06

| Act | P06 hop | Label |
|---|---|---|
| 2 | Governed context (24 tables, baseline gate) | `LOCAL` |
| 3 | Access over a real MCP call | `LOCAL` |
| 5 | Propose, approve, execute, verify, audit | `SIMULATED` |
| 6 | Agent answering from governed data (Foundry + Fabric analog) | `LOCAL` (required) |
| 7 | Simulated outage, breaker, read-only fallback | `LOCAL` data in `HYBRID` mode, with a reason |
| 10 | Proof: zero LIVE and zero cloud operations | `LOCAL` |

Act 6 runs `LocalSalesAgent`: a deterministic agent that answers allow-listed questions over the
synthetic `mfg-sales-v1` data with one DuckDB tool call (`local_sales_query`) and records
`grounded: true`. It is labeled `LOCAL` and is a teaching analog of a grounded tool call - not a
language model and not a simulation of Foundry.

## What exists, and what arrives later

- **Now (opt-in):** a read-only `LiveFabricProvider` (`FFIA_FABRIC_LIVE=1`, hybrid or live
  environment, git-ignored bindings) and pinned Fabric MCP profiles in `config/mcp/profiles.yaml`.
  Both are tested LOCAL and REQUIRE TENANT VALIDATION; the offline demo never uses them.
- **Now (opt-in):** `FoundryAgentProvider` behind the `AgentProvider` port calls an existing
  Foundry agent version through the project Responses API (`FFIA_FOUNDRY_LIVE=1`, hybrid or live
  environment, a `foundry:` binding). Hybrid falls back to the LOCAL agent after 240 s with
  `fallback_used` and a reason; live never falls back. The live agent with the Fabric data agent
  tool reproduced the baseline when called from an SDK script; the routed path, live evaluation and
  the `monthly-insights` workflow over the live agent REQUIRE TENANT VALIDATION.
- **Later:** Foundry cloud evaluators in CI, Agent Framework checkpointing and human-in-the-loop
  pauses, and Foundry IQ knowledge sources. See ADR-0013.
