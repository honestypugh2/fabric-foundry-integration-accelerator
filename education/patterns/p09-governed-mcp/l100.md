## What it is

An **MCP server** offers *tools* to an AI client (Copilot, Claude Code, a Foundry agent). Each
tool has a name, a description and typed inputs. The client discovers the tools and the model
decides when to call one.

**Governed MCP** means each tool is treated like a production API:

```text
 Agent / developer tool
        │  "which tools exist?"         ← discovery shows only the allow-list
        ▼
 MCP server ── manifest: owner, version, read-only?, rate limit, audit, enabled
        │  typed call (no free-form SQL, shell or URL)
        ▼
 Capability ── runs with an identity that has its own permissions
        │
        ▼
 Result + audit record (correlation ID)
```

## MCP compared with an API

| | REST API | MCP tool |
|---|---|---|
| Who calls it | Code written by a developer | A model choosing at run time |
| Contract | OpenAPI | Tool name, description, input schema, annotations |
| Authority | Caller identity + API checks | **The same** — MCP adds none |

Because a *model* chooses the call, the tool surface must be smaller and safer than a typical
API: the model can be tricked by text it reads (prompt injection).

## Key ideas

- **Allow-list, not block-list.** Tools that are not listed simply do not exist.
- **Narrowest server.** Use documentation tools to learn *how*, read-only tools to see *what is*,
  and the approval flow (P08) to *change it*.
- **Read-only by default.** A tool that proposes a change is not a tool that makes it.
- **No escape hatches.** No "run any SQL", "run any command" or "fetch any URL" tools.
- **Labels.** In this repository the local server is `ffia-local`; every result is labeled
  `LOCAL` or `SIMULATED` and says no cloud operation was performed. It is **not** a Fabric MCP
  server — those are separate pinned profiles, read-only unless you opt in to authoring.
