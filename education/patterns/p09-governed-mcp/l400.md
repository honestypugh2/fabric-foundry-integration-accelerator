## Protocol behavior that matters for governance

- **Discovery is the allow-list.** A client can only call tools returned by `tools/list`; if a
  tool is not registered, there is nothing to call. Revocation means "not registered".
- **Annotations are hints.** `readOnlyHint`, `destructiveHint`, `idempotentHint` and
  `openWorldHint` help clients decide when to ask for confirmation. A client must not treat them
  as security guarantees from an untrusted server; enforcement lives in the server and backend.
- **Authorization.** For remote HTTP servers the MCP specification builds on OAuth: the server is
  a protected resource that validates tokens issued for it. Forwarding a client's token to an
  unrelated downstream API ("token passthrough") breaks that audience boundary.
- **Versions.** The specification is versioned by date; pin both the protocol expectations and
  each external server package so a server cannot change its tool set after review.

## Threat model

| Threat | Control |
|---|---|
| Prompt injection triggers a broad tool | No shell, SQL, URL or REST-proxy tools; typed, bounded inputs |
| Tool poisoning (malicious description) | Review descriptions as code; pin versions |
| "Rug pull" (server changes tools after approval) | Pin versions; re-review on upgrade |
| Wildcard grants in a bundled skill config | Rendered pinned profile, read-only default; `ffia mcp check` rejects write tools in read-only profiles |
| Agent uses MCP to self-approve | No approve/execute tools; approval is out of band (P08) |
| Runaway loop | Per-tool rate limit and timeout |
| No accountability | Audit per call; owner and version per tool |
| Confused deputy | Backend checks the caller's own permissions |

## Gateways (pattern P15)

Azure API Management can expose REST APIs as MCP tools and front remote MCP servers with
authentication, quotas and logging. Documented limits: tools only (no resources or prompts) and
no dynamic client registration in some setups. A gateway adds central policy; it never replaces
the backend's authorization.

## Failure modes in this repository

- Enabled manifest entry without code → server refuses to start (`ValueError`).
- Rate limit exceeded → `ToolError`, audited as `success: false`.
- Provider or change errors → translated to `ToolError` with the error type; no stack traces or
  secrets leak to the client.
- A stdio client launches the server with a **minimal environment**: settings such as
  `FFIA_CONFIG_ROOT` must be passed in the client's `env` block, or the server uses defaults.

## Production gaps to close

Per-caller identity on remote servers (the local server records `mcp-client`), an external
append-only audit sink, a tool registry with ownership, signed or pinned server artifacts, and
evaluation of tool selection accuracy before widening any allow-list.
