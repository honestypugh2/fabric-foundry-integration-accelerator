## Marker semantics and their failure modes

| Marker | Documented behavior | Failure mode | Control |
|---|---|---|---|
| none (initial load) | Whole file treated as INSERT | Reloading the seed duplicates every key | Seed once; validate key uniqueness |
| `0` INSERT | No duplicate-key check | Re-sent inserts create duplicates (day 5) | Prefer UPSERT for keyed tables |
| `1` UPDATE | Inserts the row if the key is missing | Out-of-order files resurrect deleted rows | Strict, contiguous sequence |
| `2` DELETE | No-op if the key is missing | Silent no-op hides a publisher bug | Reconcile counts with the source |
| `4` UPSERT | Insert or update | — idempotent on replay | Default for replayable feeds |

Rows apply in file order, and `__rowMarker__` must be the **last** column. Dropping, renaming or
retyping a column requires recreating the table folder, so schema drift is an operational event,
not a silent change.

## Why recovery is a sequence problem

Recovery needs an unbroken chain: **snapshot at watermark W** + **every file after W**.

- The drill asserts contiguity (`validate_ordering`) before replaying; a gap fails loudly instead
  of producing a plausible but incomplete table.
- Replaying sequence 9 or 11 twice adds rows (INSERT markers), while sequence 10 (UPSERT) is
  idempotent. Replay each sequence **exactly once**.
- Completion is proven with row count, key uniqueness and a **content hash** equal to the
  pre-failure hash. Byte size is not evidence.

## Assumptions in the simulation

The 7-day cleanup is modeled with a sequence counter, values are stored as text, and replaying
processed files assumes the publisher kept its own copies. Each is labeled `ASSUMPTION` in the
report so it is never mistaken for service behavior.

## Threats and AI-specific risks

| Threat | Control |
|---|---|
| An agent "helpfully" re-runs a replay | Replay is not an MCP tool; the drill is a simulation only |
| A summary hides FAIL lines | Evidence categories and PASS/FAIL checks travel with the report |
| Mirroring presented as DR | Explicit `REQUIRES TENANT VALIDATION` and documentation statements |
| Duplicates propagated to Gold and agent answers | Key checks in Silver; `detect_duplicate_records` |

## Production gaps

- Live mirrored databases, real cleanup timing and replay throughput at 100M-row scale
  **require tenant validation**; the drill's scale figures are extrapolated estimates.
- Snapshot export, retention storage and restore orchestration must be built and costed by the
  customer. Fabric Git integration will not help: it stores definitions, never table data.
