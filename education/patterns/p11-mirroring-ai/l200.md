## Components and boundaries

| Component | Responsibility | Must not |
|---|---|---|
| Publisher (your app or connector) | Write ordered, keyed change files; retain its own copies | Re-send changes as INSERT |
| Landing zone | Hold `_metadata.json` and sequential files per table | Change key columns after they are set |
| Mirroring engine (Fabric) | Apply files in order; move processed files; clean up after 7 days | Be treated as a backup |
| Snapshot job (customer-built) | Full export with watermark sequence and content hash | Skip the hash |
| Restore runbook | Restore snapshot, replay retained files, validate | Declare success before checks pass |
| Silver / Gold and agents | Consume the mirrored table | Assume source security came across |

## Identity and security

- The publisher writes to the landing zone with an identity that has write access to that
  mirrored database item only.
- The mirrored SQL analytics endpoint is read-only. Source row-level and object-level security
  and masking are **not** propagated, so access to mirrored data must be granted in Fabric
  deliberately before agents use it.

## Data flow of the drill

| Day | Event | Effect |
|---|---|---|
| 0 | Initial load without `__rowMarker__` | All rows INSERT |
| 1–4 | Updates, inserts, deletes, upserts | Normal change flow |
| 5 | Source re-sends yesterday's inserts as INSERT | **Duplicate keys** |
| 6 | DELETE then UPSERT | Duplicates remediated |
| 7 | Weekly snapshot (watermark sequence 8) | Recovery point |
| 8–10 | Changes; cleanup purges sequences 1–4 | Older files gone |
| 10 | Table lost | Restore snapshot + replay sequences 9–11 |

The **counterfactual** — only the day-0 snapshot exists — fails, because sequences 2–4 were already
purged.

## Trade-offs

- **Snapshot frequency vs cost:** a longer interval needs longer publisher-side retention.
- **INSERT vs UPSERT markers:** INSERT is simpler to publish; UPSERT makes replay idempotent.
- **Re-seed vs restore:** re-seeding is always possible but may be slow and load the source.

## Online and offline

Offline, every step is a local file operation labeled `SIMULATED`. In a tenant, the same
contract applies, but cleanup timing and replay behavior **require tenant validation**.
