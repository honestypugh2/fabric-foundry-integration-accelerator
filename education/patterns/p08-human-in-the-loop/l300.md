## Running the flow

Start the control plane (`make run-api`) and walk the flow with the REST API:

```bash
# 1. PLAN (nothing runs)
curl -s -X POST localhost:8000/api/v1/plans -H 'Content-Type: application/json' -d '{
  "operation": "create_lakehouse",
  "target": {"workspace_alias": "demo-dev", "item_type": "Lakehouse",
             "item_name": "bronze_lab", "destination": "LOCAL"},
  "reason": "Lab: governed change", "requested_by": "engineer-a"}'

# 2. APPROVE as a different person (self-approval returns 409)
curl -s -X POST localhost:8000/api/v1/approvals -H 'Content-Type: application/json' \
  -d '{"change_id": "<change_id>", "approver": "approver-b", "decision": "APPROVED"}'

# 3. EXECUTE with the approval (LOCAL → SIMULATED, then VERIFIED)
curl -s -X POST localhost:8000/api/v1/fabric/change -H 'Content-Type: application/json' \
  -d '{"change_id": "<change_id>", "approval_id": "<approval_id>", "executed_by": "scoped-writer"}'

# 4. AUDIT
curl -s localhost:8000/api/v1/audit/<correlation_id>
```

## Through MCP

The `ffia-local` server exposes `generate_fabric_change_plan` and `validate_change_plan` only.
There is no approve or execute tool, so a coding agent can draft a plan but cannot apply it.

## What the tests prove

`tests/unit/test_config_policy_changes.py` covers self-approval refusal, approval expiry,
rejected approvals, duplicate blocking, destination tampering and LIVE refusal without redirect.
