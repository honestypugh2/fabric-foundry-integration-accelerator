## Where boundaries fail in practice

| Failure mode | What goes wrong | Control |
|---|---|---|
| Confused deputy | An agent identity with broad Fabric rights answers for a user who should see less | Prefer the delegated path for reads; give agent identities only the roles the use case needs; rely on Fabric RLS/OLS, not prompt rules |
| Tool list treated as permission | "The server exposes `executeSQL`, so the agent may run it" | Allow-list tools per profile; authorization stays with identity and policy |
| Prompt injection via context | Retrieved text tells the agent to write or exfiltrate | No write tools on the reasoning path; approval out of band; evaluate with adversarial cases |
| Agent becomes the system of record | Writes land in analytics or are committed without the owning system | Scoped writer calls the business system's API; verify against it after the write |
| Silent simulation | A failed LIVE call quietly returns local data | Labels on every envelope; reads fall back only in `HYBRID` mode, as `LOCAL` data with `fallback_used` and a reason; writes never fall back |
| Evidence gaps | No trace links answer, tools and approval | One correlation ID across traces, audit and evaluation runs |

## Protocol details that matter

- MCP authorization builds on OAuth: the MCP server is a resource server and must validate the
  token's audience. A token minted for one server must not be replayed against another.
- Remote Fabric MCP servers act with the caller's own Fabric permissions; they do not elevate.
  That makes **identity selection** the security decision, not server selection.
- Foundry agents can require approval before an MCP tool call runs; per-call approval complements,
  but does not replace, a deterministic validation step and a separate writer identity.

## Resilience without dishonesty

The provider router applies a per-capability timeout, bounded retries with jitter and a circuit
breaker (three failures open it; after 60 seconds it moves to `HALF_OPEN` for one trial call).
Client errors such as an unknown table are never retried or redirected. Only reads may fall back,
and only when the environment allows it.

## Production gaps to close

- Broader tenant validation. Live reads (workspaces, items) through `LiveFabricProvider` and the
  `fabric-readonly` Fabric MCP profile were verified in one demo tenant; DAX reconciliation,
  table listing, throttling behavior and the scoped writer still REQUIRE TENANT VALIDATION.
- Foundry agents, tracing and evaluators wired to the same correlation IDs (Phase 6).
- An authorized writer identity per target, an append-only audit sink outside the app, and
  security CI that checks MCP profiles and secrets (Phase 8).
- Tenant validation of every identity path; treat today's guarantees as **SIMULATED LOCALLY**.
