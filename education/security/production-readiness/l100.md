## Five practical boundaries

1. **Customization:** an overlay selects a synthetic dataset and guides. It narrows allowed reads
   and writes without changing the neutral baseline. Start with a fictional alias.
2. **Untrusted content:** a website, document or MCP response is data, not an instruction granting
   authority. The assistant must not treat "ignore approval" inside a result as permission.
3. **Secrets:** tokens and tenant bindings belong in ignored local files or a managed secret
   store, never the browser, prompt packs or Git. Ignore rules do not excuse copying a secret.
4. **Releases:** a reviewed change passes quality, privacy, evaluation and security checks before
   artifacts are eligible for publication. A failed check blocks release.
5. **Costs:** bounded calls, quotas, budgets and capacity pause schedules reduce usage. A daily
   ingestion cap does not guarantee total spend.

The offline agent evaluation uses five known synthetic cases, including refusing an unrelated
question. It proves the deterministic local baseline behavior, not that every model response is
correct. Production needs representative evaluations and negative access tests with real roles.

## Secure deployment, gateways and overlays

Private connectivity limits the reachable network surface; managed identity limits which service
can authenticate. Neither replaces data authorization. A gateway can authenticate consumers,
enforce quotas and expose a narrow MCP tool surface, but cannot turn a model proposal into approval.
Choose it for shared governance, not just because it is available. An overlay selects synthetic
data and narrower policy while leaving real bindings outside Git. These are P14, P15 and P18:
deployment, shared access and reuse are separate responsibilities.
