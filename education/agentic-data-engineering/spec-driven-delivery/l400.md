## Specifications as experimental instruments

A prototype specification should include the hypothesis it tests, the baseline, intervention,
metrics and stopping conditions. Distinguish research uncertainty from implementation ambiguity:
some questions require an experiment rather than another design meeting.

## Quality versus completion

A requirements checklist asks whether requirements are clear, complete and consistent.
Implementation evidence asks whether behavior satisfies them. Do not let an agent check
reviewer-owned requirement items to bypass the gate.

## Threats to validity

Specs can become stale, tests can mirror implementation mistakes and generated tasks can omit
adverse cases. Use independent baselines, permission-negative tests and outage scenarios.
Include excluded outcomes and unsupported integrations in the final handoff.

## Scaling reuse

Keep use cases as validated registry entries, with private overlays for real bindings.
Reuse patterns and shared contracts rather than copying application code per scenario.
Version the specification and evaluation evidence together. Neither an approved spec nor
convergence grants production deployment authority.
