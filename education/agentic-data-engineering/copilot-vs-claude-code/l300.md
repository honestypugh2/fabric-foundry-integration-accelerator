## The shared files in this repository

```text
AGENTS.md                              single source of truth for every agent
CLAUDE.md                              contains @AGENTS.md so Claude Code loads the same rules
.github/copilot-instructions.md        Copilot summary of AGENTS.md
.github/instructions/*.instructions.md path-specific rules (applyTo globs)
.mcp.json                              microsoft-learn (http) + ffia-local (stdio: uv run ffia serve mcp)
.claude/skills/                        shared skill folder (accelerator skills arrive in Phase 7)
```

Open `.mcp.json` and note that both servers are declared once. Copilot CLI and Claude Code each
list and manage them with their `/mcp` commands, and each asks you to trust a server before using
it.

## Running the same task in both

Copilot CLI, interactive with plan mode (Shift+Tab), or headless with tight tool rules:

```bash
copilot -p "Explain silver/silver_encounters.sql and list its data-quality flags" \
  --deny-tool 'shell(git push)'
```

Claude Code, plan mode, then headless:

```bash
claude --permission-mode plan
claude -p "Explain silver/silver_encounters.sql and list its data-quality flags"
```

Both should call the same `ffia-local` tools (`inspect_medallion_architecture`,
`preview_table`) and return envelopes labeled `LOCAL`.

## The bake-off method (Phase 7)

| # | Task (synthetic data) | Correctness check |
|---|---|---|
| 1 | Design the medallion for a new source | Plan reviewed against `docs/` and the pattern catalog |
| 2 | Write a Silver transform | `ffia data build` and baseline comparison pass |
| 3 | Add a materialized-view style Gold table | Tests and `evaluate_against_baseline` pass |
| 4 | Fix a deliberately failing transform | Failing test turns green, nothing else changes |
| 5 | Produce a change plan | `generate_fabric_change_plan` output is valid and not executed |

Scorecard per run: correctness checks passed, approvals requested, unsafe actions blocked,
evidence completeness (labels, correlation IDs, plan, audit), time, and premium requests or
tokens where the harness shows them.

Rules for a fair run:

- Same task wording, same repository commit, same synthetic profile (`hc-lab-7file-v1`).
- Record harness version and model; where possible use the same model family in both.
- Several runs per task; record failures, not only the best run.
- Run `ffia privacy scan` on transcripts before storing them as replays.

## What the tests prove today

`tests/unit/test_mcp_server.py` shows the MCP surface is the same no matter which harness
connects: no approve, execute, SQL or shell tool exists.
