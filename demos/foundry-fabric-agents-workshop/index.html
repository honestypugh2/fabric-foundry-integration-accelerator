Guide 2 · Manufacturing (synthetic) · Foundry Agent Workshop

Foundry + Fabric agent workshop: from governed sales data to insights and action

A 60-minute workshop for a manufacturing customer: Microsoft Foundry capabilities and how they work with Microsoft Fabric, approaches for building and orchestrating agents, connecting internal and external data, security and governance, and the customer's own use cases. Every segment has a portal path, a code-first VS Code path and an offline path.

60 minutes Business and IT leaders, data and analytics team, architects Guide mfg-01-foundry-fabric-sales-insights Synthetic data only

Overview

Scenario. "Fabrikam Industrial", a fictional manufacturer, sells five product lines through four regions. Business teams own focus areas (product lines or the Key Account segment). Sales data lands in Fabric with real-world problems: duplicate lines, retired product codes, prices entered per box, unmapped regions. All data is synthetic.

What we show. A Fabric data agent answers governed questions over the sales semantic model. A Foundry agent uses it as a tool, adds cited public context, writes a monthly brief for each team, and explains data-quality issues while a person approves any fix. The same flow runs three ways:

  • Live (Azure connected): Foundry portal, Fabric portal, and Python in VS Code against the demo tenant.
  • Hybrid: live portals plus the local accelerator app for architecture and evidence.
  • Offline: the accelerator app and ffia mfg commands on synthetic data. Every result says LOCAL.

The one-line architecture. Fabric provides governed data and meaning. Foundry provides reasoning, tools and orchestration. Entra identity, guardrails and human approval provide authority. Tracing and evaluations provide evidence.

By the end, the audience can

  • Explain what Microsoft Foundry is (models, Agent Service, tools, evaluations, guardrails) and how it relates to Microsoft Fabric (data, semantic models, the Fabric data agent).
  • Compare ways to build and orchestrate agents: portal prompt agents, workflows, code with the Foundry SDK or Microsoft Agent Framework, and Copilot Studio.
  • Connect internal data (Fabric, SharePoint, AI Search, APIs, MCP) and external data (web grounding) and state the security trade-offs of each.
  • Answer the five customer questions: Foundry + Fabric demo, competitor web data, monthly insights, data quality, and licensing.
  • Identify two or three of their own use cases and the pattern that fits each.

Reference architectures

Architecture patterns

P01 · Fabric Data Agent + Foundry MIXED

A Foundry agent asks a governed Fabric data agent for answers over structured Fabric data.

Use when: Conversational questions over curated lakehouse, warehouse or semantic-model data.

Avoid when: When a fixed report answers the question, or when service-principal-only access is required.

Authority: End-user identity through on-behalf-of; Fabric permissions decide what is visible.

P06 · Fabric + Foundry enterprise agent (anchor) MIXED

An application agent combines Foundry knowledge and Fabric context with identity, evaluation, audit and approval.

Use when: Production assistants that read governed data and may propose actions.

Avoid when: Simple Q&A that one data agent or report already answers.

Authority: Entra identity plus policy; humans approve high-impact actions.

P04 · OneLake as Foundry knowledge MIXED

Unstructured files in OneLake become cited knowledge for agents through Foundry IQ.

Use when: Retrieval over documents with citations, alongside structured analytics.

Avoid when: Numeric questions that belong to governed measures.

Authority: The search service's managed identity indexes content; plan entitlement trimming explicitly.

P08 · Human-in-the-loop governed action GA

Retrieve, cite, reason, propose, validate, apply policy, approve, scoped write, verify, audit.

Use when: Any write to a business system or Fabric item.

Avoid when: Never skip it for high-impact, destructive, regulated or financially material actions.

Authority: Human approver plus a narrowly scoped writer identity.

P10 · Medallion + AI GA

Bronze preserves, Silver conforms, Gold serves semantic models and agents.

Use when: Every analytical foundation that agents will consume.

Avoid when: Never let agents read Bronze for business answers.

Authority: Layer-level permissions.

P12 · Direct Lake + semantic model + AI GA

Semantic models over OneLake tables give agents governed measures and relationships.

Use when: Governed measures for reports and agents.

Avoid when: When tables are not yet modeled with clear grain and keys.

Authority: Model permissions and RLS/OLS.

P14 · Secure enterprise Foundry + Fabric GA

Private networking, managed identity, Key Vault, monitoring and policy around the solution.

Use when: Production deployments.

Avoid when: Treating the demo topology as production.

Authority: Entra, RBAC and network controls.

P15 · APIM AI, MCP and tool governance GA

A central gateway for authentication, quotas, routing, versioning and telemetry.

Use when: Many consumers, shared quotas or a central tool registry.

Avoid when: A single app and a single model, where the gateway adds only latency and cost.

Authority: Gateway policies plus backend authorization.

P16 · Evaluation + observability MIXED

Traces and evaluations become quality gates for agents and data.

Use when: Always, before and after release.

Avoid when: Never optional for production.

Authority: Release owners.

Questions and answers

Can we see a demo of Foundry + Fabric working together? LIVE

Yes, in three ways (Part B). Each one uses the same Foundry agent and the same Fabric data agent.

  • Portal: a Foundry prompt agent with the Fabric data agent tool answers "Which product line grew fastest last month?" The run details show the Fabric call and the answer.
  • Code-first: fabric_sales_agent.py creates the same agent with the Foundry SDK and runs it from VS Code.
  • Offline: ffia mfg brief prints the governed numbers the agent reads, labeled LOCAL.

How it works: the Fabric data agent (GA) turns a question into SQL or DAX over the lakehouse and semantic model, runs it with the user's permissions, and never writes data. The Foundry tool that calls it is in preview. It uses the signed-in user's identity (on-behalf-of); service principals aren't supported for it. The data agent and Foundry project must be in the same tenant, and the data sources on same-region capacities.

Sources: Use the Microsoft Fabric data agent tool in Foundry Agent Service, Fabric data agent concepts, Foundry Agent Service overview

Foundry can add external data. Could we use it to pull publicly available data from a competitor's website? What security concerns should we know? DOCUMENTED

What it does. Grounding with Bing Search and the web search tool let an agent search the public web and answer with citations. That suits questions like "summarize this month's public news on steel prices" or "what did competitors announce publicly". It is search grounding, not a crawler: it does not download or mirror a website. Bing Custom Search (preview) restricts results to domains you allow-list. A browser automation tool exists too, but driving a competitor's site with it raises the same legal questions as scraping.

Is it allowed? Public does not mean free to reuse. Respect each site's terms of use and robots rules, and involve your legal team. Microsoft requires you to display the website and Bing query URLs with grounded answers (Bing use-and-display requirements).

Security concerns and controls:

  • Data leaves the boundary: the query the agent sends, with the resource key, goes outside the Azure compliance and geo boundary, under Bing's terms. The Data Protection Addendum doesn't apply. Never put internal numbers, customer names or plans in a query; instruct the agent and test for it.
  • Prompt injection: web pages can hide instructions. Use guardrails and Prompt Shields, keep web-grounded agents separate from agents that can act, and never let web content trigger a write.
  • Accuracy and attribution: require citations, show sources, and keep a person in the loop for decisions.
  • Scope: restrict domains with Bing Custom Search, or disable live web access where it isn't needed.
  • Cost: Bing grounding is a separate resource billed per transaction.

Alternative for sensitive use: have analysts curate approved public documents (price lists, filings) into Fabric through a reviewed pipeline, and let agents use only that governed copy.

Sources: Use Grounding with Bing Search tools with the agents API, Use web search tool in Foundry Agent Service, What is Toolbox in Microsoft Foundry?

Could Foundry monitor sales data and send business teams monthly insights on their focus areas? LOCAL

Yes. This is a strong first use case. The pattern (MFG-01, step 4):

  1. Focus areas live as data, in a business-teams table: team, product lines or segment, recipients.
  2. Schedule: once a month, a Logic Apps Recurrence trigger (GA) runs a workflow that calls the Foundry agent (the Logic Apps agent action is preview). Alternatives: an Azure Functions timer running the Foundry SDK (GA), or Foundry routines.
  3. Numbers: the agent asks the Fabric data agent for each team's revenue, month-over-month and year-over-year change, target attainment, margin and top movers, under a delegated identity.
  4. Insight: the agent writes three insights and one action, flags data-quality issues that affect the numbers, and passes guardrails.
  5. Delivery: the Teams or Outlook connector sends the brief; every run is traced.

On the synthetic data, Enclosures is 143% of target with bookings up about 56% month over month. Run ffia mfg brief to see all four briefs.

Simpler options:

  • Power BI subscriptions with Copilot summaries (preview), when a report summary is enough.
  • Fabric Activator alerts (GA), for threshold events between monthly briefs.

Watch for:

  • Use a dedicated identity design for unattended runs, because the Fabric tool needs a user identity.
  • Test the brief against known answers before it goes out.
  • Start with one team.

Sources: Automate Microsoft Foundry agents with workflows in Azure Logic Apps, Routines in Foundry Agent Service, What is Fabric Activator?, Create report subscriptions with Copilot summaries, Use the Microsoft Fabric data agent tool in Foundry Agent Service

Can Foundry identify data-quality issues within Fabric semantic models and help clean or correct the underlying data? LOCAL

Identify: yes, with the right tools.

  • The Fabric data agent can answer data-quality questions ("how many shipped lines have no ship date?") because it queries the data. But it is strictly read-only: it never creates, updates or deletes data.
  • Systematic detection belongs in Fabric:
  • Semantic Link in a notebook (list_relationship_violations, find_dependencies) checks data against the model's relationships.
  • Materialized lake view constraints enforce rules in Silver.
  • Microsoft Purview data quality scans profile lakehouse tables.

Help clean: yes, with approval. A Foundry agent can read the findings, explain the business impact ("these 5 lines inflate September revenue"), and propose a correction. A data steward approves it (Foundry supports a human-in-the-loop approval step, in preview). A reviewed Fabric notebook or pipeline then applies the fix in the Silver layer, and the semantic model refreshes.

Don't let an agent edit the semantic model's data or silently change records. Fix it upstream, with an audit trail.

In this demo: ffia mfg quality finds all nine injected issue types, with exact counts and a proposed correction for each (LOCAL).

Sources: Fabric data agent concepts, Detect, explore and validate functional dependencies in your data, Data quality in materialized lake views, Data quality supported sources (Microsoft Purview Unified Catalog), Add a human-in-the-loop approval step

What is the licensing structure for Foundry? DOCUMENTED

There is no separate Foundry license. Foundry is pay-as-you-go Azure consumption on your subscription.

  • Models: priced per million input and output tokens. Deployment types are Global, Data Zone or regional Standard (pay per token), Provisioned throughput (reserved capacity), and Batch (discounted).
  • Agent Service: the agent runtime is not charged separately; you pay for the model tokens it uses.
  • Tools with their own meters:
  • Grounding with Bing (per transaction, separate resource);
  • file search (vector storage);
  • code interpreter (sessions);
  • Azure AI Search (its own resource).
  • Safety and evaluations: content safety is billed per record; evaluations consume model tokens.
  • Partner models (for example Llama or Mistral) are billed through Azure Marketplace.

Fabric is separate and capacity-based: an F SKU, pay-as-you-go (can be paused) or reserved with a discount. The Fabric data agent and Copilot in Fabric run on that capacity and need F2 or higher.

Who uses it changes the license:

  • A custom app or Teams bot built on Foundry needs no per-user AI license.
  • Copilot Studio uses Copilot Credits.
  • Microsoft 365 Copilot experiences need Microsoft 365 Copilot licenses.
  • Microsoft Agent 365 (GA) is licensed per user for agent governance.

Exact prices vary by region and change; we'll share a cost estimate from the Azure pricing calculator for your volumes.

Sources: Foundry Agent Service FAQ (pricing), Fabric trial capacity, Overview of Microsoft Agent 365

What's the difference between Foundry, Copilot Studio and Microsoft 365 Copilot? DOCUMENTED
  • Microsoft 365 Copilot is the ready-made assistant in Microsoft 365 apps.
  • Copilot Studio is low-code: build agents that live in Teams and Microsoft 365, with connectors and Copilot Credits.
  • Foundry is pro-code and enterprise: any model, full control of tools, identity, networking, evaluations and deployment, billed by consumption.

They connect. A Foundry agent can be published to Teams or Microsoft 365, and the Fabric data agent is available in all three.

Sources: What is Microsoft Foundry?, Foundry Agent Service overview

Which agent-building approach should we start with? DOCUMENTED

Start with a portal prompt agent plus one tool (the Fabric data agent) to prove value in days. Move to code (Foundry SDK or Microsoft Agent Framework) when you need source control, tests and CI/CD. Use workflows or multi-agent orchestration only when one agent with tools can't do the job. Use Copilot Studio when the experience must live in Teams and makers will own it.

Sources: Foundry Agent Service overview, Microsoft Agent Framework overview, AI agent orchestration patterns

Does the agent see data the user isn't allowed to see? DOCUMENTED

No. The Fabric data agent uses the user's credentials, and row-level and column-level security still apply. The Foundry tool passes the user's identity (on-behalf-of).

Sources: Use the Microsoft Fabric data agent tool in Foundry Agent Service, Fabric data agent concepts

Where is our data stored and processed? DOCUMENTED
  • Your Fabric data stays in Fabric.
  • With the standard agent setup, agent state (threads, files, vectors) is stored in your own Storage, AI Search and Cosmos DB, with private networking.
  • Model processing follows the deployment type you choose; Data Zone keeps processing in, for example, the US data zone.
  • The exception is Bing grounding, which leaves the Azure boundary by design.

Sources: Set up private networking for Foundry Agent Service, Use Grounding with Bing Search tools with the agents API

How do we know the agent's answers are right? DOCUMENTED

Build an evaluation set of real questions with known answers. Run Foundry evaluators for groundedness, relevance and task adherence before every change. Reconcile numbers with the semantic model. Trace every run in Application Insights.

In this demo, every brief number reconciles with the governed baseline (ffia mfg brief).

Sources: Built-in evaluators in Microsoft Foundry

Can agents take actions, like updating a forecast or creating a ticket? DOCUMENTED

Yes, through tools: OpenAPI, Azure Functions, Logic Apps or MCP. Treat every write as a governed change:

  • least-privilege identity;
  • a human approval step for anything material;
  • logging.

Read-only first, then actions with approval.

Sources: Add a human-in-the-loop approval step, What is Toolbox in Microsoft Foundry?
