# Governed Fabric change (this repository)

Fabric skills (for example `e2e-medallion-architecture`, `spark-cli`) teach *how* to call Fabric.
This skill decides *whether, where and with what evidence*. MCP access is not authority; Entra
identity, policy and a human approval are.

## 1. Classify the request

| Request | Path |
|---|---|
| "How do I…", item schemas, API shapes | Read-only docs: `fabric-docs` MCP profile or Microsoft Learn. No tenant call. |
| "What exists…" | Read-only tenant metadata: `fabric-readonly` profile, or `ffia fabric readiness`. |
| Create, upload, publish, run | **Change**: follow steps 2–7. Never call a write tool or `az rest --method post/put/patch/delete` first. |

Before every cloud call, state the **provider, server and exact tool**.

## 2. PLAN (no cloud writes)

Produce a plan through the control plane, which checks policy and duplicates:

```bash
ffia demo offline                        # see the governed flow end to end (LOCAL/SIMULATED)
```

Or call the `ffia-local` MCP tool `generate_fabric_change_plan`, then `validate_change_plan`. The
plan names the operation, the target workspace **alias** (never a raw ID in chat), the item name,
the destination (`LOCAL` or `LIVE`), the risk, the rollback and the evidence required.

## 3. VALIDATE

- Confirm the tenant and workspace: `ffia fabric readiness` (GET only).
- Check for duplicates by name and type in the bound workspace. If one exists, stop and ask.
- Notebook code must come from a reviewed definition (`fabric/workspace/*.Notebook`, generated by
  `ffia notebooks render`) or be shown in full for review first.

## 4. APPROVE

Ask the user explicitly. Show the plan and wait. A different person approves: in the app, the
change rehearsal on each guide step (`/guides/<guide>/<step>`) or `POST /api/v1/approvals`. The
requester cannot approve their own change. Model intent is not approval.

## 5. EXECUTE

Only the approved operation, only in the approved workspace. If the live writer is not configured,
report `UNAVAILABLE`. **Never silently fall back to a LOCAL simulation** for an approved LIVE write.

## 6. VERIFY

Re-read the result: the item exists exactly once with the expected name and type, row counts match
`data/synthetic/expected/<profile>.json`. A tool description, a configured server, a portal run or
a matching byte size is **not** evidence.

## 7. AUDIT and report

Report what ran with its label (`LIVE`, `PREVIEW`, `LOCAL`, `SIMULATED`, `UNAVAILABLE`), the
provider and tool, the verification result and the rollback. Never print tokens, tenant,
workspace or item IDs.
